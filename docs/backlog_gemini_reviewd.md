## 4. P0 候选 (逐项展开与落地决议)

### OUTBOX-1 发件箱与关键请求的确认闭环

* **决策状态**：**做**

* **建议优先级**：P0 | **工作量**：M | **依赖**：无（与 REQ-1 合并落地）

* **用户痛点**：弱网/切网关时消息静默丢失；用户看不到“到底发出去了没有”。

* **我们现状**：

  * `outbox.flush()` 只要 `client.send()` 返回 true 就删条目；`send()` 只代表写入本地 socket。`src/transport/outbox.ts:98-102`

  * `sent` 帧回显 `requestId`（网关 0.11.1：`lib/index.mjs:561/626-629`），但 App 只把它用于语音新建，不打标 outbox 条目。

  * outbox 是模块级单例、全局 key、条目无 `gatewayId`；任何 conversation client ready 都会 flush 全部。`src/transport/outbox.ts`

  * 切网关只清 sessions/queues/pending，不动 outbox。`App.tsx:1005-1024`

* **拍板方案**：

  1. `OutboxItem` 持久化 `requestId` + `gatewayId`；

  2. flush 后标“已发送待确认”，收到同 `requestId` 的 `sent` 才删；收到 error 标失败可重试；

  3. 15s 未确认标“未确认（点按重试/移除）”，**不自动盲目重发**以免造成重复执行；

  4. 切网关只 flush 当前 `gatewayId` 的队列。

### CONN-1 连接探活、socket 守卫、前后台/切网补数据

* **决策状态**：**做**

* **建议优先级**：P0 | **工作量**：S | **依赖**：无

* **用户痛点**：界面显示“已连接”，实际收不到帧；切网/回前台后要等 50-75s 才恢复；旧 socket 的迟到帧污染状态。

* **我们现状**：

  * `watchForeground` 只把 `lastFrameAt` 重置为现在并补一个 ping，没有 pong 截止。`src/transport/gateway-client.ts:265-273`

  * `watchNetwork` 只在“socket 已空且已有 reconnectTimer”时立即 open；socket 半开不处理。`src/transport/gateway-client.ts:285-296`

  * 心跳看门狗 25s × 2 轮，最坏约 50s。`src/transport/gateway-client.ts:207-226`

  * `onmessage` 没有 socket/generation 守卫（`onclose` 有）。`src/transport/gateway-client.ts:136-168`

* **拍板方案**：

  1. 抽一个共享 `probe()`：回前台/网络恢复立即发 `ping`，**4.5s 内未收到任何帧**就主动 close + 立即重连（`attempt=0`）；

  2. 网络状态监听加 1.5s 防抖，避免 WiFi/5G 切换瞬间重连风暴；

  3. `onopen` / `onmessage` / `onerror` / `onclose` 全部校验 `socket === this.socket`；

  4. `ready` 后主连接自动补发 `sessions`。

### CONN-2 候选地址回退 + 握手截止 + 鉴权失败停止

* **决策状态**：**做**

* **建议优先级**：P0 | **工作量**：M | **依赖**：CONN-1 的守卫

* **用户痛点**：局域网入口超时后不会回退公网；反复“接受后立刻断”的代理造成 1s 一次重连风暴；token 失效仍无限重试。

* **我们现状**：

  * `SavedGateway.endpoints` 字段写了但重连时无任何逻辑消费。

  * `open()` 没有握手截止；`onopen` 立即 `attempt=0`（还没收到 `hello` 就清零了退避计数）。`src/transport/gateway-client.ts:107-134`

  * `4003` 只提示后继续按退避重连，仍带旧 token。`src/transport/gateway-client.ts:180-187`

* **拍板方案**：

  1. 每次 `open()` 设握手截止（私网 4s / 公网 12s），**只有收到 `hello (authenticated: true)` 或 `paired` 才重置 `attempt = 0`**；

  2. 收到 `4003` 停止自动重连，顶部提示“设备授权已失效，请重新配对”；

  3. 重连时优先尝试上次成功地址（`lastGoodUrl`），失败则在 `endpoints` 中轮换。

### HIST-1 历史本地缓存 + 离线可读 + 原子写

* **决策状态**：**做（核心心流项）**

* **建议优先级**：P0 | **工作量**：M | **依赖**：无

* **用户痛点**：冷启动/离线/切会话时正文空白，每次都要看着转圈等网络；右侧弧形转盘（`ArcDial`）拨动切会话时体验被白屏打断。

* **拍板方案**：

  1. **L1 内存热缓存**：在模块级 `Map<string, ChatMessage[]>` 缓存最近打开的 8 个会话，保证 `ArcDial` 切会话 **0ms 瞬时渲染**；

  2. **L2 磁盘缓存**：按 `history-${gatewayId}-${sessionId}.json` 存最近 150 条事件（只存文本与附件引用，不存 base64），用临时文件 `move` 保证原子写；

  3. 进入会话时若命中 L1/L2，**不设 `loading=true`、不清空屏幕**，直接渲染缓存，同时后台发 `history` 并在到达后用 `mergeSnapshot` 无感对账更新；

  4. 采用固定上限（最多保留最近 15 个会话的磁盘文件）自动 LRU 清理，**不做**存储清理 UI。

### APPROVAL-1 审批安全与反馈

* **决策状态**：**做**

* **建议优先级**：P0 | **工作量**：S/M | **依赖**：无

* **我们现状 (全部代码核实)**：

  * `TriageSheet.tsx:327` 的高危审批仍是普通 `onPress`（点开大卡后可一键放行，绕过了 `ApprovalDock` 的 0.5s 长按充能）。

  * 首页语音命中唯一 pending approval 且识别到“同意”时直接发 `approval-response`，没有校验 `approvalRisk`。`App.tsx:567-586`

  * 审批被拒/发送失败只写 `interactionError`，但 `ApprovalDock` 不显示该错误。

  * `approval`/`question` 都是单值 state，多个同时挂起会互相覆盖。`src/ui/SessionScreen.tsx:634-640`

  * 切会话的 reset 没清 `pinnedOnceRef/followRef/atBottomRef/quote/trustedDirs`，旧会话的引用/信任目录会串进新会话。`src/ui/SessionScreen.tsx:294-325`

* **拍板方案**：

  1. **修复会话串台**：在 `SessionScreen.tsx` 切 `session.sessionId` 的 effect 中彻底重置 `pinnedOnceRef`、`followRef`、`atBottomRef`、`quote`、`trustedDirs`、`graceRef`、`decidedId`；

  2. **统一高危长按门禁**：`TriageSheet` 底部批准按钮在高危时同样启用 0.5s 长按充能；首页卡片语音遇到 `approvalRisk(approval).level === 'high'` 时，宠物气泡提示“高危命令，请点进卡片长按确认”，拒绝语音盲批；

  4. **队列化**：将 `approval` / `question` 改为数组队列（展示队首，角标提示剩余条数）。

### 13.1 总体判断与建议顺序

原评审强调克制、复用已有界面、避免把 App 做成重型控制台，方向值得保留；但第 11 节把弱网丢消息与连接问题放在动效、导航收缩和乐观跳转之后，Codex 认为顺序值得调整。远程操作的核心首先是：**用户知道消息是否被接受、会话没有串台、批准的是明确的请求**；其次才是切换和阅读体验。

以下是**讨论顺序建议，不是排期或承诺**：

| 顺序建议 | 候选项 | 理由与第一版边界 |
| --- | --- | --- |
| 1 | `APPROVAL-1` 的审批目标绑定、会话隔离与失败反馈 | 审批操作会影响宿主；先解决错误对象、保护不一致和状态串会话。完整队列另行验证和讨论。 |
| 2 | `OUTBOX-1`、`CONN-1`，以及必要的 `CONN-2` / `REQ-1` | 防止待发内容丢失、跨网关误发和假在线；先做回执关联、持久化可靠性和基本连接恢复，再讨论候选地址轮换及阈值。 |
| 3 | `FLOW-1`、`HIST-1` | 胶囊是用户已经反馈过的阅读问题；进入会话清空正文、等待网络的代码路径也已确认。先明确展开与阅读位置语义，再做有边界的缓存。 |
| 4 | `VOICE-1`、按测量结果处理 `PERF-1/2` | 修录音启动/取消竞态、异常清理和转写失败复位；流式性能先在真实长回答上测量，再决定节流和列表参数。 |
| 5 | `DIR-1`、`SEARCH-1`、`FLOW-6` 等 | 有潜在价值，实际顺序取决于用户使用频率；尽量利用现有入口，先验证最小方案。 |

`FLOW-4` 的 Android 系统返回处理可作为独立的小修复提前讨论；进出动画需另行设计和验证，不必与返回处理捆绑。产品方向变化、具体风险确认方式、实际交付顺序仍由用户决定。

### 13.2 审批与会话隔离：建议优先讨论的最小范围

**已核实的代码事实：**

1. 展开卡 `TriageSheet` 的批准使用普通 `onPress`，`ApprovalDock` 的高危操作已有长按保护；展开卡的决定仍经过悔棋窗，不能描述成点击后必然立即发送。两条入口的确认强度不一致。见 `src/ui/dock/TriageSheet.tsx`、`src/ui/dock/ApprovalDock.tsx` 和 `src/ui/SessionScreen.tsx` 的 `decideApproval`。
2. 首页语音转写完成后，根据录音 job 中的 `sessionId` 再查该会话当前唯一的待办；如果录音针对审批 A、转写期间 A 已被处理，**同一会话内**又恰好只剩新的审批 B，对 A 说的“同意/拒绝”可能发给 B。它不会因此选择其他会话的审批；如果目标会话此时没有唯一审批，识别文本会作为普通消息尝试发给原会话。现有整句匹配、否定/疑问处理及唯一待办限制有一定保护，但没有绑定原始审批 ID。见 `App.tsx:555-588`、`src/protocol/pending.ts:113-118`、`src/protocol/voice-decision.ts`。
3. `SessionScreen` 切会话时复用组件，重置中未清除 `quote`、`trustedDirs`、`pendingSends`、语音请求及部分滚动状态。旧引用可能进入新消息；目录信任也可能跨会话影响自动放行；旧待发回显可能显示到新会话，旧转写迟到时可能通过当前 `sendRef` 发送。自动放行另有低风险、目录匹配和去重条件，不等于所有新审批都会自动批准。见 `src/ui/SessionScreen.tsx:540-553,844-876,1850-1860`。
4. 审批回执 `accepted:false` 会设置 `interactionError` 并撤销本地审计回显，但不复位 `decidedId`。当前 `InteractionSheet` 的审批入参为 null；没有 question 时，审批错误不会通过该面板显示。若本地仍保留该审批，Dock 可能继续处于 busy 状态。见 `src/ui/SessionScreen.tsx:643-655,1070-1079,2264-2273,2368-2383`。
5. 会话页的 approval 与 question 是两个独立单值：**同类型**同时挂起会覆盖，二者不会直接互相覆盖。全局已有按会话和 `rpcId` 管理的 pending 模型；control `hello` 会清空全局 pending 再等待回放。会话页重连后的陈旧交互仍需对账。并发同类型请求在实际宿主上的发生频率尚未复现。

**Codex 的候选边界：**语音开始时绑定目标 `rpcId / approvalId`，转写完成后再次核对目标仍待处理；批准入口采用一致的风险确认；切会话隔离引用、目录信任、语音任务等状态；失败或失效可见且操作状态正确。已有风险识别是启发式规则，未命中不应当作安全证明；首页 pending 信息是否足够判断风险，也须先核实，不能直接假设 `approvalRisk` 一定拿得到完整字段。

**切会话时不能简单清空 `graceRef`**：它保存已决定但尚未发出的审批，直接清掉可能吞掉用户决定；应先明确切换时提交还是撤销，再处理展示状态。完整审批队列、重连对账与风险分类可分开讨论，优先复用现有 pending 模型。

**建议验收场景：**切会话、审批被其他端处理、转写迟到、断线发送失败及服务端拒收，均不能让决定落到错误请求、吞掉用户决定或显示虚假的成功。

### 13.3 发送与连接：回执不是去重保证

**已核实的代码事实：**

- `src/transport/outbox.ts` 的条目没有 `gatewayId` 或 `requestId`；`flush()` 发出的帧也没有 `requestId`，只要 `send()` 返回 true 就移除条目。`App.tsx:703-711` 在连接 ready 时 flush 整个单例。切网关有误投风险；写入 socket 不表示网关已接受，当前也无法按回执关联到发件箱条目。
- 会话页输入框发送的消息有 `requestId`，但首页语音消息没有；会话页 `pendingSends` 的本地回显按正文与已有历史/队列内容匹配清除，重复发送相同正文或图片占位时，旧内容可能使新回显提前消失。首页语音新建会话用布尔值等待任意 `sent`，缺少请求关联；失败后也需核实 pending 状态如何复位。见 `App.tsx:588-608,674-695`、`src/ui/SessionScreen.tsx:1616-1667,1796-1812`。
- 本机安装的 `dsh-plugin-mobile-gateway@0.11.1` 在请求带有 `requestId` 时会在 `sent` 中回显；其普通、无文件的消息路径并未把该 ID 传给宿主 `sessions.prompt` 作为请求标识。**不能把回执关联等同于普通消息具备自动重试去重。** 有文件消息及子会话路径有不同的处理，仍需按具体协议核实。
- `src/storage/persisted-state.ts` 当前先删除旧文件再写新文件，错误被捕获；`outbox` 还采用延迟写盘。异常退出可能丢失未写入的新条目，也可能在 socket 已发送但删除尚未写盘时保留旧条目并在重启后重复发送。冷启动时 `outbox.load()` 与连接 ready 的 flush 也没有显式等待关系，值得复现并核对。涉及“内容已保存”的用户预期时，两者都需要评估，不能仅调整 socket 层。
- `GatewayClient` 没有完整的旧 socket 回调守卫和握手期限；前台恢复时，socket 仍为 OPEN 则补 ping、重置心跳时间，但没有单独的探活截止，非 OPEN 时会清空 socket 并安排重连；网络恢复对半开连接处理有限。`onopen` 即重置退避计数。见 `src/transport/gateway-client.ts`。

**Codex 的候选边界：**在线与离线发送统一考虑“尚未发送、已发待确认、已接受、明确失败、结果不明”等状态；按网关隔离队列与显示；关联 `requestId`；改善落盘与错误反馈。没有回执时应保留内容并显示“未确认”，先核对历史/队列，**不要因重连就盲目重发**；人工重试也须说明可能重复。旧版无 `gatewayId` 的待发项如何迁移、能否可靠归属，需单独讨论，不能猜测或默认发往当前网关。

连接先讨论旧 socket 守卫、握手截止和前台/切网探活；候选地址校验与轮换可独立交付。文档中的 4.5 秒、私网 4 秒/公网 12 秒是候选参数，需结合实际网络测试，不是已证实的时限。已有认证 `hello` 后拉 `sessions`，不应重复补一套。

**`4003` 不能一律解释成“设备授权已失效”**：本机 0.11.1 发布包的代码同时用它表示重新开启鉴权及设备撤销。应结合原因、当前凭证、后续鉴权结果和实际客户端可获得的信息设计恢复；不要把所有情况机械归为同一文案和停止策略。

### 13.4 胶囊、历史与性能：先确认行为，再确定参数

- **`FLOW-1`**：多层折叠属实，且 `group.ts` 在正文出现等边界把活动改组为胶囊。Codex 倾向于外层展开直接展示步骤列表，长思考/工具输出仍按需展开；中文标题可显示步骤数量与失败情况。思考耗时是否有可靠数据需先核实，不能凭示例直接显示“已思考 18s”。展开层级与自动收拢造成的阅读位置变化要分别验证。`docs/HANDOFF.md` 已记录用户要讨论这一问题，但没有确认具体方案。
- **`HIST-1`**：切会话会清空 `messages` 后请求历史；有缓存可以改善等待和离线阅读。建议按 `(gatewayId, sessionId)` 隔离、记录格式版本、保留必要分页元数据、同时控制条数和字节数，并验证磁盘写入/恢复。内存热缓存可以先做，磁盘缓存可紧随其后；“0ms”“绝无白屏”不是当前实测结果。
- **阅读窗口与缓存尾窗分开**：不要把“磁盘只保留最近 150 条”直接等同于 UI 只允许存在最近 150 条，否则用户翻出的旧消息可能被裁掉。当前历史请求没有 `requestId`，翻页与最新页靠本地状态区分；重连、超时或迟到响应交错时，对分页游标和滚动位置的影响值得验证。要验证缓存与 `mergeSnapshot` 的合并、换会话的迟到读写、离线过期提示、分页与滚动位置。见 `src/ui/SessionScreen.tsx:475-510,894-899,922-971`。
- **`PERF-1/2`**：流式 chunk 会更新状态，`MarkdownView` 对变化的文本重新解析；但当前没有本轮真机掉帧测量。`FlatList` 已经存在；调整参数并不能保证 60fps。先选择长回答和长会话场景测量，再按瓶颈决定合并更新、文本渲染或窗口大小。
