## 0. 一句话

本轮把「审批拍板」和「连接真实性」两项做成了**可验证的真机行为**（不是只跑单测），

## 1. 本轮的做事方式

1. **独立复核**：不预设 Gemini / Codex 任意一方正确，逐条回到代码与协议核对，
   区分「源码确认 / 可能但未复现 / 产品假设 / 未验证」。
2. **逐项决策**：把第 5 节列出的 10 个问题交给用户逐条确认，用户全部认可后才动手。
3. **实现 + 真机验证**：每个结论都要有真机/真网关数据支撑；造条件的工具留在
   `.scratch/`，可复跑。

### 3.2 第二项：连接真实性

做了什么（`src/transport/gateway-client.ts` + 新增 `src/transport/connection-policy.ts`）：

- 握手截止：从创建 socket 起 12s 内没有 `hello`/`paired` 就断开重连；只有收到 `hello` 才清退避。
- 旧 socket 守卫：`onopen/onmessage/onerror/onclose` 全部校验 `socket === this.socket`。
- 探活：回前台/切网恢复后发 ping，5s 内没有任何帧就主动断开重连。
- 网络切换：第一次网络回调只建基线，**之后任何 online 事件**都当作一次网络切换（1.5s 防抖）。
- 4003/4004：停止自动重连，并区分「设备被撤销」和「重新开启鉴权」；App 提示改为引导重新配对。
- `send()` 对 socket 在检查与发送之间关闭的情况做 try/catch；重连定时器不再叠加。
- 删掉 App 层重复的「回前台就 connectWith」effect，统一由客户端探活负责。

真机验证（真机 `<device>` / 真网关 `<gateway>` / 假网关 3999）：

| 场景 | 实测 |
|---|---|
| 冷启动 | 2 个连接（主 + control），「已连接」 |
| 后台 35s 回前台 | 仍是 2 个连接，未等 50-75s |
| 撤销设备（4003） | clients 2 → 0，10s 内无重连；提示「设备授权已被撤销，请重新配对」 |
| **12s 握手截止** | open→close **12.001~12.015s**；重连间隔 1.026s / 2.016s / 5.014s；App 显示「连接超时，正在重连」 |
| **5s 半开探活** | 回前台 → **5.118s** 主动断开 → **1.009s** 后重连 |
| **WiFi 关** | **+2.313s** 发出探活 ping → **+5.008s** 断开 → **+1.02s** 重连 |
| **WiFi 开** | 关联完成后 +2.67s 探活 → **+5.005s** 断开 → **+1.005s** 重连 |

### 3.4 第三项：语音健壮性

做了什么（提交 `70c278e` + `66909a1`）：

- **一份状态机**：首页语音球与会话页麦克风共用 `src/ui/voice/useVoiceInput.ts`；
  上限、提示、复位只有一处实现。App/PetStage/SessionScreen 只负责手势与展示。
- **启动竞态**：按「意图 ref」判断，不依赖异步的 `recording` state；
  收尾窗口（停录 + base64 编码，长录音可达数百 ms）加 `finishingRef` 互斥 + `utteranceRef`
  令牌——极快松手不再卡死，松手后立刻重按也不会出现「两段在途、两段都丢」。
- **上限**：`recordLimitSeconds = min(maxDurationSeconds, floor((maxAudioBytes-44)/32000))`，
  剩 1 秒就停（`RECORD_MARGIN_SECONDS`）；录音中显示 `0:12 / 0:20`，最后 10 秒琥珀色 +
  一次 tick 震动。被 JS 卡顿拖过头时 `clampWav()` 按实际时长就地截断再发。
- **到点自动停（用户拍板 B）**：不代发。文字回输入框——目标会话已打开时走一次性
  投递通道合并进草稿；目标为新会话时挂起文字、按 `session-create` 的 requestId 认领，
  失败/断线退剪贴板，绝不静默丢字。
- **失败语义**：`send()===false`、断线、`speech/unavailable|busy|timeout|invalid-audio`、
  空转写各自有提示并立即复位 `transcribing`；上滑取消/离开会话页会对在途转写发
  `speech-cancel`，不再让它占住网关槽位（否则下一句直接吃 `speech/busy`）。
- **评审补丁**（对未提交版本做了对抗式评审，22 个 agent，12 条发现，1 条被驳倒后不采纳）：
  被拒的按住不再改写上一段语音的投递目标（`begin()` 返回是否被接受）；providerId/language
  开录时钉住；selection 指向不可用 provider 时回退到 ready 的；`startFileRecordingAsync`
  失败时关掉已开的流（麦克风常开）；首页卡片被网格重排挤出时卸载收尾；上限计时显示

### 3.5 新发现（未修）：取消回合后，排队的消息不会自动续跑

用户 2026-11-02 真机发现。**根因在宿主 `@deepseek-ai/dsh@0.2.1-rc.3` 的
agent-loop，不在 App、也不在网关**，源码级确认：

1. 手机点「停止」→ 网关 `session-cancel` → 宿主 `sessions.cancel()` →
   `agent.cancel({kind:'user'}, {keepInbox:true})`（**故意保留**队列，注释与网关
   PROTOCOL.md 都写明 "retain queued work"）。
2. agent-loop 正常回合结束时，`turn()` 末尾发现 `inbox.hasPending` 会直接返回
   true 继续下一回合（队列自动续跑就靠这条路径）；而 **abort 走的是异常路径**，
   跳过这段判断。
3. abort 之后要不要唤醒只取决于 `wakeRequested`，而它只在「消息到达时 abort
   信号已经 aborted」的情况下才置位——健康运行的回合里排队的消息不会置位。
   结果：队列原地搁浅，直到下一条消息的 `send()` 起一个新 driver，
   这才顺便把最早的排队消息先跑掉（所以表现为「必须再发一条才会触发」）。

关于「多条排队能否打包发送」：**不能打包**。`claim()` 对 `next-turn` 每次只取
1 条（`mutate("next-turn", 0, 1)`），每条排队消息各自成为一个独立回合、顺序执行
（真机日志 `agent/inbox/spliced` 的 `start:0 removedCount:1` 序列可以逐条对上）。
打包语义只存在于 `next-step`（插话/steer），不是排队。

修复方向都属于宿主侧（例如 cancel 保留 inbox 时同时置 `wakeRequested`，或
`kick()` 收尾时发现 `hasPending` 也唤醒）；App/网关当前协议里没有「唤醒队列」
的帧可用，建议反馈给宿主/网关作者。记录见 `docs/BACKLOG.md` §11 的 QUEUE-1；
**已提 issue**：`Clarklevis1995/dsh-plugin-mobile-gateway#37`（2026-11-02，
含复现步骤、协议时间线与源码定位）。

### 3.6 第四项：发件箱回执关联（已落地，提交 `62469e3`）

做什么：

- **回执闭环**：离线条目创建时就有 `requestId`（随 `message` 帧发给网关），
  `sent`/`error` 回执照它归位——`sent` 删条目、`error` 标失败记原因；不再「写进 socket 即删」，
  `sending` 超 20s 没回执按派生状态显示「未确认」。
- **网关隔离**：条目创建时记 `gatewayId`，`flush` 只发当前活动网关的条目、写不进 socket 即停下保序；
  旧数据（升级前遗留、无 `gatewayId`）在 flush 时按当前活动网关**收养一次**（等价旧版本行为；
  严格版「待归属选择」没做，记 BACKLOG）。
- **手动重试，不自动重发**：failed / 未确认可重试；重试换新 `requestId`（迟到的旧回执不会命中
  新一次）。不自动重发是硬约束——网关对普通消息不去重，自动重发会出重复消息。
- UI 四种状态：`待发送 · 联网后自动重发`（删除）/ `已发送，等确认…` / `未确认 · 可能没送达`
  （重试/移除）/ `发送失败：原因`（重试/移除）。

真机验证（本机网关；真断线 = `taskkill` 停 dsh web，设备 `<device>`）：

| 步骤 | 实测 |
|---|---|
| 真断线期间发消息 | 气泡「outboxtest」+「待发送 · 联网后自动重发」+「删除」，composer 清空 |
| 网关重启（2~3s 后 App 自动连上） | flush 自动补发：网关 `mobile message accepted text="outboxtest"` **只一条**（07:44:47.724Z，legacy 07:44:47.425Z 连上） |
| `sent` 回执到达 | 离线条目消失，变成正常回声气泡（无状态脚注）；agent 侧也确认「outboxtest 收到…一份」 |
| 再重连一次（网关换成 detached 进程） | 没有重发：`mobile message accepted` 计数 27 → 27 |

单测覆盖（未真机复现）：`failed`（error 回执）、「未确认」20s 派生、手动重试换 requestId、
跨网关跳过、断点保序、旧条目收养、坏数据丢弃（10 条，`src/transport/__tests__/outbox.test.ts`）。

**观察（未修）**：USB 通道配对（`adb reverse tcp:3080`）下，`svc wifi disable` **不是真断线**——
socket 走 USB 不受影响，NetInfo 却把 UI 打成「设备已离线/连接已断开」，此时发送仍直发成功
（第一轮测试的 `outboxofflinetest` 就是这么发出去的）；且「网络恢复」事件没有把 error 打回
ready 的路径（探活成功只防假死，只有握手 `hello` 才 `emitState('ready')`），横幅会一直挂到
下一次真重连。LAN 场景（WiFi 断即真断）自愈正常。记 BACKLOG §11 CONN-3；
造真断线的正确姿势见 §6.2。

### 3.7 第五项：历史 L1 内存缓存 + 评审修复（已落地，提交 `d6d02d4`）

做什么：

- **L1 模块**（`src/transport/history-cache.ts`）：模块级 LRU，按 `(gatewayId, sessionId)` 存最近 8 个会话，
  存不可变替换后的数组引用（零拷贝）；空数组=删除；移除网关时按前缀清命名空间。不做磁盘层（L2 等冷启动频率测量）。
- **会话页接入**：挂载时先摆缓存（有缓存不进 spinner），新鲜 history/snapshot 走 `mergeSnapshot` 对账，不整体替换；
  messages 每次变化写穿缓存（在途工具行不写入——见修复 3）。
- **评审**：改动上了一轮对抗性评审 workflow（3 维度找问题 → 每条 2 个独立验证者反驳），
  5 条发现（去重后 3 类）全部确认，均在提交前修复：

| # | 发现（都已修复） | 修法 |
|---|---|---|
| 1 | **pinnedOnceRef 重新上膛**：缓存命中时 pin effect 先消耗闸门，挂载 effect 又把它重置 → 之后第一次翻页/补消息的三连 `scrollToEnd` 无视 followRef，把正在看旧消息的用户拽回底部（触发条件：对账后长度不变，即安静会话重进） | 删掉挂载 effect 里的重置（闸门挂在组件实例上，重挂载天然是新 ref，重置行本多余） |
| 2 | **缓存-新鲜窗口有洞时错序**（高）：离开期间新增 >1 页（宿主 `DEFAULT_MAX_MESSAGES=50`）→ 缓存 1..100 + 新鲜 245..300，补洞页经 `prependHistory` 被插到最前 → 时间线错乱并写回 L1 不自愈；断线重连路径本就有同病 | 翻页改用 `mergeSnapshot` 按 seq 落位（顺带治重连路径）；视口补偿只在「整页比已加载最早还早」时做（唤醒只写不读的 `oldestSeqRef`，挂载时以缓存最小 seq 为种） |
| 3 | **幽灵工具行**（低）：在途工具行（output 未到）写进缓存，重进时若落在新鲜窗口之外，tool/result 永远配不上对（`mapHistory` 只在本页内回填）→ 永久转圈 | `cacheHistory` 写入时过滤在途工具行（无该行才保持零拷贝） |

删除 `prependHistory`（唯一调用点改为 `mergeSnapshot`，语义是其超集）；`seqOf` 导出复用。
单测：`mergeSnapshot` 契约 7 例（含洞填充回归）、`history-cache` 8 例（含幽灵行）、`chat` 原用例全绿——
26 suites / 240 tests；tsc 0；lint 0。**真机未验**（见 §3.7 验证清单在 `.llmdoc-tmp/hist1-scenarios.md`）。

### 3.8 REQ-1：关键请求超时 + 可重试空态（已落地，提交 `d6d02d4`）

协议核实（npm 0.11.1 为准确认）：`history` 带 `requestId` 时成功/错误帧都回显（`lib/index.mjs:1525-1537`）；
`session-create` 强制要求 requestId（1493-1494）；纯客户端可修，BACKLOG §9 成立。

- **历史首屏**：subscribe+history 带 requestId 一把发，单飞守卫；15s 无回包（或 error 帧 `requestType=history`、
  或 send 失败=断线）→ 撤 spinner，给「历史没加载出来 + 重试」空态（不再永转圈）。老网关不回显 requestId 时
  「在途期间任何 history 帧都算回包」兼容。
- **会话新建**（列表页 + 目录选择器）：15s 兜底撤 `creating` + 文案 + 宠物提示；send 失败同样落地；
  `session-created`/`error` 按 requestId settle。
- **语音新建两条路径**：等 `sent`（`voiceCreateRequestRef`）15s → 清 ref + 提示不自动重发；
  等 `session-created` 的语音草稿 15s → 退剪贴板（复用 rescue 语义）。
- **不做**：`session-stats`（面板空着不阻塞，超时后唯一动作是静默=没改）；不自动重试（与 OUTBOX-1 一致，网关不去重）。
- 假网关补 `no-history` / `no-create` 吞帧模式 + `session-create` 支持（含 requestId 回显），
  冒烟 14/14 PASS——超时路径的「不回包」前提可造。真机未验。

### 3.9 FLOW-1：活动胶囊中文摘要 + 消除套娃折叠（已落地，提交 `552cf9d`）

### 3.10 会话页滚动修正：翻历史不被打断 + 回合结束锚定（已落地，提交 `402c63f` + `254ef57`）

真机验证中用户当场裁定两处不合理，逐条修复：

- **① 翻历史被拽回底部**：`assistant-stream` 是每步一对 start/end，原实现每步 start 都
  无条件 `followRef=true`——停在历史中间的读者一有新动作就被拉回底部。改为只在贴底
  （`atBottomRef`）时续跟随，拖动留下的 `follow=false` 保住。
- **② 回合结束停在距底约 1/3 屏、终答被折线切掉**。修的过程用 `adb logcat` 埋点挖出真根因：
  `onContentSizeChange` 的 atBottom 分支用 `scrollToEnd`，目标按 JS 侧滞后的内容高度算
  （trace：目标 7551 vs 真底 7636，落地差 86px）→ `atBottom` 被误判成假 → 跟随链中途断掉、
  本轮剩余 500+px 生长全部不跟。与 follow 分支合并为一句
  `scrollToOffset({ offset: 本次量到的真实高度 })`（超出被原生钳到真底）。
- **锚定**：`turn/end` 且贴底时，把「最后一条用户消息」滚到视口第一行——折叠胶囊 + 正文随后，
  即用户点名的收官布局；停在历史中间的读者不动。

真机验证（证据与截图见 `.llmdoc-tmp/hist1-scenarios.md`「①② 修复真机验证」）：
停车场景步进开始/回合结束**头部以下像素 0 diff**；盯屏场景锚定正中且两帧 bit-identical；
根因修复后停车回归重跑全过。

## 6. 验证方法与可复用工具

### 6.1 假网关（本轮新写，`docs/tools/fake-gateway.mjs`）

端口 3999，三种模式，HTTP 控制面：

```
node docs/tools/fake-gateway.mjs                    # 起服务
curl "http://127.0.0.1:3999/mode?value=no-hello" # no-hello | half-open | normal
curl "http://127.0.0.1:3999/log"                 # 连接/关闭/ping 时间线
curl "http://127.0.0.1:3999/pair?host=usb"       # 生成假网关配对二维码（usb | lan）
```

- `no-hello`：只发 `paired` 不发 `hello` → 造「TCP 已连但握手不完成」。
- `half-open`：发 `hello` 之后不回 ping → 造半开连接。
- `normal`：正常回 pong / sessions。
- `paired` 只在首连（带配对码）时发，否则 App 的 `paired` 分支会重启 control，造出假 churn。

跑通一次「真机按住说话 → 转写」需要三件事（本机已配好）：

1. profile 装 `@deepseek-ai/dsh-experimental-voice-input-bundle@0.1.7-alpha.1`，
   并在 `~/.dsh/profiles/web/compatibility.json` 给它的 4 个包开对 `0.2.1-rc.3` 的版本豁免；
2. `cordis.patch.yml` 把 `speech-to-text-sensevoice` 的 `modelOrigin` 换成
   `https://hf-mirror.com`（三个模型文件 ~241MB，国内直连 huggingface 会超时）；
3. 模型下载完成前 `preparation.phase=unprepared`，App 显示「语音还在准备」是正常现象。

排查看 `speech-catalog` 帧里的 `providers[].preparation.phase`（**在 preparation 底下**）
与 `selection.providerId`；本机默认 `sensevoice-local`。
