## 3. 详述

### 3.1 J1：真机领取 + 真 Worker 发布

App 冷启动连上本机网关后，control hello 带 `rendezvous-v1`，App 发 `rendezvous-config`；
网关为手机设备生成 43 字符 key 并立即 poke。PC 侧用 `devices.json` 里的 key 派生路径，从真 Worker
取回密文并解密：

```json
{"v":1,"rev":1793772061247,"gatewayId":"<gatewayId>","endpoints":["wss://...trycloudflare.com/ws/mobile"]}
```

与设计一致：Worker 只看到密文与随机路径，无 gatewayId/手机标识。

### 3.2 J3：两条断线路径

**A. 强制断 USB（同一端点）**：`adb reverse --remove tcp:3080` 只移除监听，**既有 socket 不会断**
（这是本次踩到的第一个测试坑）；改用 `adb kill-server` 才把连接打断。App 连续失败后从真 Worker
取得同一个 tunnel URL 并重连；网关菜单从 `127.0.0.1:3080` 变为 `max-evans-...trycloudflare.com`。
从 App 回前台到重新连上约 8s（断网期间 App 在后台，计时含后台挂起，不作为纯恢复时延）。

**B. 端点变更（真实场景）**：kill 网关进程并重启（Quick Tunnel 每次重启换 URL）：

| 时刻 | 事件 |
|---|---|
| 0s | 旧网关被杀，App 连接断开 |
| 3.6s | 新网关进程启动 |
| 59.3s | 新 tunnel `<old-tunnel>...` online |
| 113.2s | 地址簿完成重发（60s 发布 tick） |
| 147.8s | App 从真 Worker 拿到新 URL，自动连回 |

总恢复 **2m28s**，落在设计 §10 的 2~3 分钟预算内。期间 App 保留缓存会话、显示
「连接中断，正在重连 · 点这里重连」，没有弹窗打断；宠物呈闭眼/沮丧表情。恢复后网关菜单显示新地址。

### 3.3 J4：WiFi 开关

WiFi 开（连上 test hotspot）再关：连接全程可用；切网瞬间网关侧短暂出现 3–4 条 socket（新旧并存），
旧 socket 在心跳窗口内退出，最终稳定 2 条。无崩溃、无重连风暴。

### 3.4 J10：冷启动

`force-stop` 后重新启动 Expo Go，约 5–9 秒经已保存的 tunnel URL 连上；没有重新扫码、没有回配对页。
说明 App 侧 `rendezvous.seenRev/url` 与网关侧设备 key 的持久化都正常。

### 3.5 J5：撤销 + 重新配对

撤销手机设备后：网关立即以 4003 `device revoked` 关闭连接；App 顶部显示
「设备授权已被撤销，请重新配对 · 点顶部网关名」，停止自动重连；Worker 记录 404。
重新配对使用当前 tunnel 作为 publicUrl（App 选路优先 wss），全程蜂窝 + VPN，约 3s 连上；
新设备 `e6476d7f-b8d8-44ea-8a25-3f3fc54b611b` 获得新 key 并出现在 Worker。

### 3.6 附带修复

PC 侧 E2E 发现：发布成功一次后 `rendezvous.lastError` 不会清空，`/mgw/status` 会一直挂着启动时的
`no endpoints to publish`。已改为「成功 PUT 且未丢 endpoint 时清空」，并在
`test/rendezvous.test.mjs` 加断言（12/12 通过）。该改动目前只在本地仓库，未提交。

### 8.5 手机真机旅程（2026-11-04 17:00 前后）

设备 4238a31c（Expo Go，Android），蜂窝网络 + VPN；`VPN interface` 的 UID 列表包含 Expo Go。

1. **网络前提**：不开 VPN 时，手机侧 `workers.dev` 被 DNS 污染（解析到 `162.125.32.10`，TLS 超时），
   App 的 `fetchAddressBook` 拿不到 body；开 VPN 后 Worker GET 200。这与 issue 里写的国内蜂窝限制一致。
2. **手动 → 托管迁移是死角**：手机原记录指向旧的手动 Worker（`dsh-rendezvous.<account>.workers.dev`），
   网关已切到 `dsh-rendezvous-<random>...`。`decideAdoption` 按「URL 不同 → conflict」拒绝新配置，
   手机只能反复读旧 Worker 的冻结记录（`decodeAddressBook` 因 rev 未推进返回 null）。
   **按设计只能重新扫码一次**；本次用真实 QR 重新配对后恢复正常，`rendezvous-config` 采纳为
   `decision=same`（托管 URL）。
3. **换址自愈**：`POST /mgw/cloudflare/restart` 于 16:56:28 换出
   `wss://<new-tunnel>.trycloudflare.com/ws/mobile`；Worker 在 16:56:31 发布新记录；
   App 在 16:57:49 的刷新周期解出新 URL 并立即重连，`connectedClients=2`。**全程未扫码，约 81 秒**。
4. **恢复后的完整动线**：进入会话 → 历史正常 → 发送 `rendezvous_ok` → 收到「收到：rendezvous_ok」；
   返回列表 → 强制停止 App 冷启动 → 直接「已连接」，未再扫码。
5. 待决：手动/托管切换（或重新部署产生新 Worker 名）时的 URL 变更，是否需要一条「已认证连接上的显式迁移」
   路径；当前规则会让这类用户重扫一次。管理面板的真浏览器视觉检查仍未做。
